# Authorized operator-budget import

This mode implements the user's revised application policy for the existing compact bundle. Provider remaining reads/writes, reset timing, and shared reservation remain null. No provider allocation is inferred. Actual provider denials and limits still stop the operation.

Hard operation limits are 1,300,000 writes, 5,000,000 reads, 150,000,000 measured database bytes, one importer/request in flight, and at most 25 new corpus batches in a tranche. Bootstrap requires the original four receipts and seeds the measured ledger with the known pilot totals: 3,860 writes and 7,431 reads. It never resets an existing ledger.

`cbank_operator_ledger` persists counters, the exact active tranche, next sequence, verification progress, the pending operation ID/body hash, and the last successful response. The operator client also saves actual returned counters and a pending request atomically, under a process lock. Timeouts retry the identical operation ID. A completed operation can replay its saved response. A still-pending operation exposes its corpus receipt and stops: an unmeasured ambiguous transaction is never silently retried or forgiven.

Ledger bookkeeping cannot atomically persist metadata about its own final update. Its final update counters are therefore returned to the client's durable measurement log. The database separately charges a conservative bound of 8 writes/32 reads per operation, covering that final update and up to three bounded recovery attempts; measured counters and these bounds are reported separately. A separate initial bound of 1,000 writes/10,000 reads covers earlier unmetered schema/viewer work. These are conservative operation charges, not fabricated measurements or provider reservations. Admission uses measured consumption plus all those bounds. Actual overhead above its bound stops execution. Any unavailable response measurements remain explicitly unobserved and covered by the persisted bound; unresolved data-operation measurements stop execution.

Each import reservation uses that batch's manifest index-write estimate, plus receipt/accounting margin; reads use a conservative row-based bound. During import, 2,500,000 reads and 40,000 writes remain reserved for verification/activation, plus database-size headroom. D1 data and the original immutable receipt commit atomically. The server hashes the exact allowlisted batch bytes. No arbitrary SQL operation exists.

The initial expanded tranche is sequences 4–7. All 1,000 new payloads must pass canonical hash verification before opening the next tranche. Subsequent tranches are at most 25 batches. Full verification reconstructs all 100,800 canonical problems in fixed pages and compares independently derived page digests with the preserved serving database; it checks publication tuples, all 260,400 memberships, pool/release digests, counts, foreign keys, and every topic/difficulty selection cell. Activation requires all those persisted verification checkpoints and performs a final guarded transaction.

The signed endpoint uses a fresh Ed25519 key and real expiry, and no browser-origin request is accepted. Keys and private data remain outside source/public assets. The compatible legacy game stays deployed until activation and matching compact-bank deployment. Remove the operator environment keys and redeploy after completion. Provider throttling is respected with bounded retries; cumulative limits are never raised automatically.

The latest provider-allowance runner and its tranche checks remain available. `mode: 'operator-budget'` is an explicit separate authenticated execution branch, and rejects `local: true`.

Production gameplay verification uses the same bank selector, game API/engine, quota code and hosted Firestore service, with three fixed operator-authenticated test identities. Every test collection path is prefixed, including queries and transaction operations, so existing players and leaderboards are unaffected. D1 calls are metered through the same cumulative ledger. The checks cover all four modes, shared snapshots and answer order, canonical references, scoring, repeated claims, history and error responses. They exercise the production services but do not replace browser sign-in tests. Test records and quota keys are deleted afterward; temporary runtime access is removed at completion.

After full hosted verification, activation uses a separate 750,000-read reservation. The unchanged guard measured 403,719 reads and 2 writes against a full local D1 copy, so this bound retains 86% read headroom. It refines the phase estimate; it does not raise the 5,000,000-read operating limit or assert provider capacity. Actual hosted counters remain mandatory.
